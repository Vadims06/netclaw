# Teaching NetClaw to Speak Auvik — A Read-Only MSP Monitoring MCP

*Draft milestone post (Constitution Principle XVII). Authored collaboratively by John and Claude. WordPress MCP is not configured in this environment — publish manually.*

## What we built

Feature **036** adds an **Auvik API MCP server** to NetClaw: a read-only, FastMCP/stdio server that turns Auvik's network-monitoring API into 20 tools the agent can call, organized around the four things MSP operators actually ask about — **inventory, network alerts, lifecycle, and performance** — plus a billing/usage view of inventory. It ships with four skills (`auvik-inventory`, `auvik-network-alerts`, `auvik-lifecycle`, `auvik-performance`) and a full 348-test suite.

## Why it matters

Auvik is where a lot of MSPs keep ground truth about *what's on the network and how it's behaving*. Wiring it into NetClaw means an operator can ask, in plain language — "is core-sw-01 healthy?", "what critical alerts fired overnight for the Dallas client?", "which devices are past end-of-support?" — and get an answer without touching the Auvik UI or memorizing an API.

## Two decisions that shaped the design

**Operators speak in names, not IDs.** Auvik addresses everything by opaque IDs, but nobody says "show me device 242216279026467843." So identifier resolution is a first-class, cross-cutting capability: every tool accepts a name, hostname, or IP, resolves it to the right Auvik ID, and — when a name is ambiguous — returns the candidate matches and asks rather than guessing. A wrinkle we found in the spec: Auvik's device/network/interface list endpoints have *no* server-side name filter, so resolution fetches and matches client-side (which is exactly why the next decision mattered).

**Real result sets span many pages.** Auvik paginates with JSON:API cursors, and its `meta.totalPages` is deprecated. The client auto-follows `links.next` and aggregates every page up to a safety cap, flagging truncation with a continuation cursor — so a "list the devices" answer is the *whole* list, not a silently truncated first page.

**Read-only by construction.** The one mutating endpoint Auvik exposes (`alert/dismiss`) was deliberately left out. There are zero write tools, no `post`/`put`/`delete` anywhere in the client — verified by test and by source grep. Observability shouldn't be able to change the thing it observes.

## How it was built

Spec-Driven Development end to end (Constitution XVI): a ratified spec, then a plan set (research, data-model, tool contracts, quickstart, tasks), then test-driven implementation executed by a fleet of focused subagents with a two-stage review after each unit. That review caught two real defects before they spread — a subagent that hallucinated Auvik's `deviceType` enum, and a planning assumption that a name filter existed where it didn't. Every turn was recorded in an immutable GAIT session log (Constitution IV).

## Lessons learned

- **Pin your enums to the source, and test the count.** "It's a non-empty set" let a hallucinated enum through; "it has exactly 48 values including `multimedia`" did not.
- **Verify the API's filters before you design resolution around them.** The missing `filter[deviceName]` would have been a runtime surprise; catching it in review made it a five-minute spec edit.
- **Make the model state its assumptions.** The strongest review signal was subagents *documenting* the judgment calls they made (which field to match a network name on, how to handle an ambiguous entity) — that's where a human's eye lands fastest.
